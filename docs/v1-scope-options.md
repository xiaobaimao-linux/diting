# v1.0 范围对焦：三个方案备料（W6 D5）

> 日期：2026-10-12。用途：v1.0 出口定义决策备料，**只摆事实与取舍，不给推荐排序**。
> 依据：docs/prd.md（M0–M8）、docs/kernel-compat-matrix.md（§2 主矩阵 / §4 待实测清单）、
> docs/calibration-w5.md §2（W18 出口原口径）、W6 实测（规则包 19 条 + 22 用例、CIS 40 项引擎、AI 告警升级）。

## 现状盘点（三方案公共前提）

- 已落地：遥测（network/dns/privilege/ns）、FIM、规则引擎 DSL v1 + core 规则包 16 条（+examples 3 条 = 19）、
  22 攻击用例两轮回归、CIS 引擎 40 项全判定 + HTML/JSON 报告、AI 资产发现（GPU/模型文件/AI 进程）、AI 告警升级。
- v1.0 剩余缺口（按 kernel-compat-matrix.md §4 与 W5 口径）：
  1. **perf buffer 降级版**：`priv_watch`/`net_watch` 的 perf 降级未实现，4.18/5.4 档黄格未落地（5.4 实测：ringbuf map EINVAL，挂点无恙、败在事件通道）；
  2. **兼容矩阵实测**：RHEL8 4.18 的 BTF backport 与 lsm_kprobe 加载均待实测；5.10/6.x 真机未跑过；
  3. **规则包广度**：挖矿（M3-4）、防御规避（M3-5）类规则未覆盖；G1（无 cmdline）等表达力缺口限制规则深度；
  4. 工程化：G16 单实例锁、Syslog 通道、RSS 瘦身（常态 139.3MB，红线 150MB）。
- 速率参照：W1–W4 周均 2.75 计划项；W5/W6 均为 14 项清单全完成，但含"引擎类工作持续被低估"的前科（W3 性能攻坚吃掉 W4 前两天）。

## 方案 A：原计划（W18 出口，全量范围）

- **范围**：维持 W18 出口原口径不变——遥测 + FIM + 规则引擎 + CIS 基线 + 攻击用例 ≥90% 检出，
  **含 perf 降级版**（priv_watch/net_watch perf buffer 通道）与**三系统兼容矩阵实测**
  （Ubuntu 20.04/5.4、RHEL8/4.18、5.10+ 各一档真机）。
- **时间**：W18 ≈ 2027 年 1 月上旬。距今 12 周，按当前速率容量充裕。
- **风险**：
  - perf 降级版是"内核类"工作，历史上此类工作被低估；4.18 档依赖 RHEL8 BTF backport 实测，
    若小版本无 BTF 则 4.18 档整体降级为"设计目标、不支持"，范围被动收缩；
  - 兼容矩阵需备三档真机/VM 环境，环境准备本身吃工期；
  - 缓冲被侵蚀的传导路径：perf 降级延期 → 兼容实测顺延 → 出口前突击。
- **社区故事线**：v1.0 即打出"4.18–6.x 四档内核全覆盖"的兼容性招牌，对国内企业用户
  （RHEL8/CentOS8 存量）吸引力最大；但发布最晚，前 12 周社区无可 tagging 的里程碑。

## 方案 B：收缩版（砍 perf 降级，声明 ≥5.8，兼容只做 Ubuntu 系）

- **范围增删**：
  - 删：perf buffer 降级版开发、4.18/5.4 档兼容承诺（kernel-compat-matrix 黄格红格整体转为
    "v1.x 候选"，文档口径改为"内核 ≥5.8 全功能，<5.8 不支持"）；
  - 留：其余 v1.0 口径不变；兼容实测只跑 Ubuntu 系（20.04 无 ringbuf 亦出局 → 实际为 22.04/24.04 两档）；
  - 5.4 已有的 kprobe 文件监控降级（lsm_kprobe，实测可用）保留代码但不进 v1.0 验收口径。
- **时间**：预计 2026 年 11 月底（≈W12），比 A 提前约 6 周。
- **风险**：
  - Ubuntu 20.04（5.4）被切出支持面——该版本仍在 ESM 支持期，存量用户升级前无法用本产品；
  - "声明 ≥5.8"把 Debian 11（5.10 ✓）/openEuler 等发行版的兼容性留为未实测灰区；
  - 砍掉的 perf 降级版若 v1.1 补做，需重新排期内核类工作，团队估时偏差可能重现。
- **社区故事线**：最快可发布的开源故事——"eBPF 主机安全 v1.0，规则包 + CIS + AI 资产开箱即用"，

  早 6 周抢占关注度；代价是兼容性叙事弱一档，README 支持矩阵第一行就是限制声明。

## 方案 C：AI 加强版（AI 模型保护规则包进 v1.0）

- **范围增删**：
  - 增：M4-1 模型完整性保护（模型权重/tokenizer/配置哈希基线，复用 FIM 引擎）、
    M4-2 模型加载监控（open+mmap 非白名单加载告警）、配套模型保护 DSL 规则包与攻击用例
    （模型篡改/批量外拷场景）；AI 资产 → 告警升级 → 模型保护 形成完整 AI 安全闭环；
  - 减/缓：perf 降级版与 RHEL8 实测可缓至 v1.1（同 B 的口径收缩），为 AI 项腾容量。
- **时间**：预计 2027 年 1 月中下旬（≈W19–W20），比 A 晚 1–2 周。
- **风险**：
  - M4-2 的"模型加载监控"依赖 open+mmap 挂钩与路径识别，mmap_file 钩子 5.9+（仓库已 __weak 兼容），
    5.8 档行为需实测，存在新的内核类估时风险；
  - 模型文件目录的 FIM 注册依赖 G6（inode 注册机制），大模型目录批量注册的工程细节未验证；
  - 出口最晚，且新增范围本身可能再滑。
- **社区故事线**：差异化最强——"开源主机安全里第一个把 AI 模型保护做进 v1.0 的"，

  直接对应 PRD 的 M4 定位，对 AI 基础设施用户有独立传播点；但故事线变长，
  "主机安全工具"与"AI 安全工具"两个标签需要在发布材料里讲清楚主次。

## 公共决策点（与方案无关，W7 需拍板）

- DSL 文件类规则依赖 FIM inode 注册才有事件源（G6/D4 联调发现）：自动注册 or 加载期警告，
  影响规则包"开箱即用"口径，三方案均受其约束。
